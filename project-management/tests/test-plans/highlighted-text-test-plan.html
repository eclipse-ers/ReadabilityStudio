Highlighted-Text Window Test Plan

The standard-project highlighted-text windows were rebuilt to render as adaptive HTML instead of the previous rich-text / Pango control.

What to watch for

  • The windows now follow the app’s dark / light theme on screen.
  • They honor the selected report theme, including the colored accent bar on the legend.
  • Saving to RTF and copying to the clipboard still work, and always come out paper-white — a format meant for pasting into a word processor or printing, regardless of the on-screen theme.
  • Printing and Save-as-PDF always come out on white paper.
  • Very large documents display reliably.
  • Highlight colors and the two highlight modes (background vs. foreground) still apply.

Platforms

Exercise every section on all three desktop platforms. Each renders these windows with a different underlying engine, so theme, print, save, large-document, and Unicode behavior can differ.

Suggested test fixtures

  • Doc ASmall English sample. A few paragraphs with known hard words, a passive-voice sentence, a wordy phrase, a misspelling, and some Dolch words. Fast to eyeball for correctness.
  • Doc BBook-length English document. Tens of thousands of words, for the large-document and performance cases.
  • Doc CLeading indentation and blank lines. Verifies whitespace and line breaks are preserved.
  • Doc DShrinks after re-analysis. A short document that becomes much shorter (e.g. exclude most text), for the shrink-refresh case.
  • Doc ENon-English / Unicode. Spanish or German with accented letters, plus a non-Latin script such as Greek, Cyrillic, or CJK, to exercise Unicode content.

01Rendering & correctness

Open Doc A. Enable every relevant test / section (DC, Spache, H-J, 3-syllable, 6-char, a custom word test, grammar highlighted report, Dolch). Visit each window in the sidebar.

  • 1.1

    Each of the 9 windows renders with visible highlighted words (no blank page, no raw markup shown as text).

  • 1.2

    The correct words are highlighted per window (e.g. 3-syllable window highlights only 3+ syllable words; Dolch window highlights Dolch words; grammar window highlights long sentences, errors, and wordy phrases).

  • 1.3

    The legend appears as a banner card with a colored accent bar down the side, matching the look of the app’s other reports.

  • 1.4

    Legend swatches match the highlight colors actually used in the body, and their labels are correct (e.g. difficult words, error / wordiness categories, the 7 Dolch categories).

  • 1.5

    Whitespace & line breaks preserved (open Doc C): paragraph indentation and line breaks appear; text is not collapsed to a single run. Blank lines create vertical spacing.

  • 1.6

    Body font family, size, and weight reflect the text-view font (see 8.3), not a default font.

  • 1.7

    No white flash when a window is first shown; it appears already painted.

  • 1.8

    A window whose section is toggled off (e.g. disable the 6-char report) is removed from the sidebar; toggling it back on re-creates it.

02Highlight colors & modes

Tools › Options › highlighting settings. There are two modes, background highlight and foreground highlight, plus individual color pickers for default / error / style / excluded and the 7 Dolch categories.

  • 2.1

    Background mode, change the default highlight color (e.g. to yellow). Re-open the windows: highlighted words show the chosen background color with legible text on the swatch.

  • 2.2

    Foreground mode, change the default color: the highlighted text itself is recolored (no background fill).

  • 2.3

    Change each category color (error, style / wordiness, excluded, and each of the 7 Dolch categories) and confirm the corresponding words and legend swatches update.

  • 2.4

    Switch between background and foreground mode and confirm the rendering style flips for all windows without needing a re-analysis.

  • 2.5

    Choose an excluded-text color; confirm excluded / ignored regions render with it (grammar and unfamiliar-word windows).

03Theme, dark / light, and the accent color

Two independent scenarios: the OS light / dark setting, and the app’s report theme (Tools › Options › report theme).

  • 3.1

    Switch the OS to dark, then light, with a window open. Page background and text follow the theme; no re-analysis required.

  • 3.2

    Background mode across themes: swatches keep their fixed color and stay legible in both light and dark.

  • 3.3

    Foreground mode across themes: pick a light highlight color, then confirm the highlighted text stays readable in both light and dark.highest risk

  • 3.4

    Legend accent color: with a window open, change the report theme (e.g. default to fruit salad). The legend accent bar recolors to the new theme’s accent color without re-analyzing the document.key case

  • 3.5

    Change the theme with multiple projects open; confirm every open project’s windows update, not just the active one.

  • 3.6

    After a theme change, confirm body text and highlight colors are also consistent with the new theme, not just the legend.

04Print & PDF

  • 4.1

    Print preview a window (e.g. grammar). Output is on white paper, highlights legible.

  • 4.2

    Print to a physical or virtual printer — same white-paper result.

  • 4.3

    Save as PDF — resulting PDF is white-paper and readable.

  • 4.4

    Print a window while the app is in dark mode — still prints light, not a dark page.

  • 4.5

    Accept the loss: no custom header, footer, or watermark on these windows (expected).

05Save (HTML / RTF)

Save from a window’s toolbar or menu. The file type in the save dialog is the format choice (HTML / RTF / PDF).

  • 5.1

    Save as .htm; open the file standalone in a browser — it renders correctly, adapts to light / dark, with the right highlights.

  • 5.2

    Save as .rtf; open in Word and LibreOffice Writer — opens on white paper, highlight colors legible in both.

  • 5.3

    Foreground-mode light color in RTF: with foreground mode and a light color, saved RTF shows the color darkened so it reads on white (not washed out).

  • 5.4

    Save as .pdf from the save dialog — white paper, readable.

  • 5.5

    Save the grammar and a Dolch window as RTF and confirm multi-category coloring survives the round trip.

  • 5.6

    Save Doc E as .htm and .rtf; confirm accented and non-Latin characters render correctly in both (no garbled text).

  • 5.7

    Filter list depends on the window: a highlighted-text window’s save dialog offers HTML, RTF, PDF; a summary report window (test scores, statistics) offers only HTML, PDF — no RTF entry.

  • 5.8

    Filter drives the extension: type a filename with the wrong extension (or none) and pick a different filter — the saved file gets the filter’s extension, and the content matches that format. Check each filter on each platform (macOS / GTK don’t rewrite the name themselves).

  • 5.9

    Save to a path in a folder that doesn’t exist yet — reported as a failure rather than silently doing nothing (the manual Save does not create folders; the Lua save does — see 11.1).

06Copy / clipboard

  • 6.1

    Copy from a window, paste into Word and LibreOffice Writer — rich formatting arrives with paper-white highlight colors in both.

  • 6.2

    Copy always copies the whole window, by design: select a partial range and Copy, then paste into Word and LibreOffice Writer — the entire report arrives, not the selection. Confirm this on all three platforms, and that nothing crashes.

  • 6.3

    Paste into a plain-text editor — sensible plain text, no markup leakage (no CSS from the page’s <style> blocks, no tags).

  • 6.4

    Copy from Doc E and paste; confirm Unicode characters survive to the clipboard.

  • 6.5

    Copy from a summary report window (test scores, statistics) — still pastes as HTML / plain text (no RTF buffer exists for those); no crash.

07Combined report / Export all

The export dialog’s format combos changed: text reports now offer HTML / RTF / PDF, there is a new “Export summary reports as” (HTML / PDF) for the scores and statistics windows, lists gained PDF, and graphs gained WebP. The combos are now driven by validators rather than read manually on OK.

  • 7.1

    Save all / Export combined HTML report; confirm the highlighted-text windows appear in the aggregated report with their correct captions.

  • 7.2

    Export-all to a folder; the per-window text files are written (HTML / RTF / PDF per the chosen text extension) and open correctly.

  • 7.2a

    Every combo round-trips: set each of text reports (htm / rtf / pdf), summary reports (htm / pdf), lists (htm / txt / tex / pdf), and graphs (png / jpg / bmp / tif / tga / gif / svg / webp), export, and confirm the files are written in that format and actually open.

  • 7.2b

    Choices persist: the combos come up on the selected values next time the dialog is opened, and after restarting the app (they are written to the options file). A value saved by an older build that is no longer in a list must not leave the combo blank or break the export.

  • 7.2c

    Summary reports vs. text reports are independent: choosing PDF for summary reports leaves the highlighted-text files in the text-report format, and vice versa.

  • 7.2d

    RTF where it belongs: with text reports set to rtf, every highlighted-text window in Words Breakdown, Grammar, and Sight Words is written as .rtf — none silently fall back to .htm. Confirm no zero-byte or mislabeled files.

  • 7.3

    Highlighting survives export: the highlighted-text sections of the combined report show their highlight colors and legend swatches — not just the plain words. Confirm the colors match the on-screen windows and the selected report theme (banner / accent), including a non-default theme (e.g. fruit salad or autumn).key case

  • 7.4

    Self-contained + adapts to light / dark: open the exported combined report standalone in a browser (no sibling style.css needed — the CSS is embedded) and toggle the browser or OS between light and dark. The page background and text follow the theme, foreground-mode highlighted text stays legible in both, and background-mode swatches stay legible in both. This holds whether the app was in light or dark mode when the report was exported (export in each mode and confirm the file adapts either way).key case

  • 7.5

    Print / PDF of the exported report stays white paper, even when the report is being viewed in dark mode.

  • 7.6

    Graph figures inside a dark-viewed report: the figures are raster images baked at export time, so they do not follow the reader’s theme. Export with the app in light and in dark mode, view each report in both, and confirm the figures stay legible (no dark-on-dark, no transparent background swallowing axis labels).

  • 7.7

    Body font: the highlighted-text sections of the combined report use the report theme’s font, not the text-view font (unlike the on-screen windows — see 1.6). Confirm this is the intended look and that nothing renders at a broken size.

  • 7.8

    Export-all with text reports unchecked — the combined report still renders, with no leftover empty highlight styling or dangling captions.

08Refresh scenarios

  • 8.1

    Re-analyze (reload source, or change an analysis option that reindexes): all windows rebuild with correct content; no stale page, no leftover from the prior analysis.

  • 8.2

    Change a highlight color or mode (section 2): windows update without a re-analysis.

  • 8.3

    Change the text-view font (family / size / weight): windows re-render with the new font; a bold text-view font does not double-bold or corrupt the grammar highlighting.

  • 8.4

    Theme change (3.4): windows update to the new theme.

  • 8.5

    Trigger several refreshes in a row on the same window — the page always shows the current content, never a progressively stale one.

  • 8.6

    Refresh Doc D (document becomes much shorter): no crash; window shows the reduced content.

  • 8.7

    Cross-project isolation: open three different projects concurrently (e.g. Doc A, Doc B, and Doc E), each with highlighted-text windows. Refresh or re-analyze each one in turn, then revisit every window in all three projects. Confirm each window shows its own project’s content — no window ever displays the highlighted text from another open project. (These windows are keyed off process-wide state and reused window IDs, so a mismatch would surface here.)key case

09Large documents & performance

  • 9.1

    Open Doc B (book-length) with all windows enabled. All windows load and render their full text (no truncation).

  • 9.2

    Loading Doc B does not spike memory to an unreasonable level while the windows build.

  • 9.3

    Note the load time on Doc B; it should be tolerable, not multi-minute.

  • 9.4

    Re-analyze Doc B a few times; confirm memory returns to baseline afterward (no runaway growth across refreshes).

  • 9.5

    Open and close several projects with these windows; confirm memory is released with the closed projects.

  • 9.6

    Cached page cleanup: refresh Doc B many times in a row, then close the project. Each refresh replaces the windows’ cached pages rather than accumulating them, and closing the project drops the rest — memory should return to baseline, not creep upward per refresh.

10Read-only guards & lifecycle

  • 10.1

    Right-click a window — no browser-style context menu (reload, save, view source, developer tools) appears.

  • 10.2

    These are read-only reports — nothing in the page navigates away or blanks the window when interacted with.

  • 10.3

    Find within a window works (find text, wrap-around); note any whole-word behavior differences from the old control.

  • 10.4

    Sidebar icon, ribbon buttons (colors, font, save, copy, print), and window selection and sizing all behave as before for these windows.

11Regression / untouched paths

  • 11.1

    Scripted (Lua) save of a highlighted window honors .rtf / .htm / .pdf and produces the same output as the manual Save. Unlike the manual Save, it creates missing folders in the target path — verify that, and that the returned success / failure value is accurate (including a path that cannot be written).

  • 11.5

    Scripted export-all uses the saved summary-report extension alongside the list, text, and graph extensions; confirm the summary reports come out in the configured format.

  • 11.2

    The other report windows (score / summary report, explanations, batch reports) are unaffected; they still render and theme correctly.

  • 11.3

    Non-English / non-Dolch project: DC, Spache, H-J, and Dolch windows are correctly absent; the language-agnostic windows (3-syllable, 6-char, grammar) still work.

  • 11.4

    Unicode content (Doc E): all windows render accented and non-Latin characters correctly in the highlighted body and the legend labels (no garbled text, no missing glyphs).
